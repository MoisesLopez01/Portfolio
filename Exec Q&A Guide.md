# Exec Q&A — Source of Trust Guide

> Weekly executive backlog signal for the **Exec Q&A** sheet.
> Generated by [`Jira Backlog.js`](./Jira%20Backlog.js) (v3.0.0).

This sheet is the **source of trust** for week-over-week backlog movement. Every number is computed directly from Jira with deterministic rules (no manual input, no edits). If a number is surprising, the JQL and math documented below make it auditable end-to-end in under 5 minutes.

## Reading the table

Each non-narrative row has 7 columns:

| Col | Name                 | Meaning                                                                                |
| --- | -------------------- | -------------------------------------------------------------------------------------- |
| A   | Signal Level         | Scope (blank = company-wide, or a Space key like `COE`, `R&D`, `Customer`, or `TOTAL`) |
| B   | Metric               | What's being measured                                                                  |
| C   | _earlier week label_ | Value for the older of the two compared weeks                                          |
| D   | _latest week label_  | Value for the most-recent completed week                                               |
| E   | WoW Δ                | D − C                                                                                  |
| F   | WoW %                | (D − C) / C × 100 (or 100 when C = 0 and D > 0)                                        |
| G   | Signal               | Plain-English direction + business interpretation                                      |

### Color code (cells E and F)

| Color | Meaning                                                      |
| ----- | ------------------------------------------------------------ |
| Green | Positive Δ or % (value went up)                              |
| Red   | Negative Δ or % (value went down)                            |
| Gray  | Zero / no change (or snapshot rows with no prior-week value) |

### Direction is metric-aware

Some metrics are "higher is better" (throughput, contributors, RPE cleared); others are "lower is better" (cycle time, blocked, % unassigned). The Signal column interprets this correctly:

| Signal word | Meaning                                      | Example                     |
| ----------- | -------------------------------------------- | --------------------------- |
| ▲ Up        | Value increased on a "more is better" metric | Throughput went up          |
| ▼ Down      | Value decreased on a "more is better" metric | Throughput went down        |
| ▲ Improving | Value decreased on a "less is better" metric | Cycle time went down — good |
| ▼ Worsening | Value increased on a "less is better" metric | Blocked items went up — bad |
| ► Flat      | No change                                    | —                           |

> **Important:** green/red on cells E/F follows the raw arithmetic sign (positive = green). For "lower is better" metrics, **trust the Signal column wording**, not the cell color, when deciding whether the change is good.

## Section-by-section reference

### ❓ Questions This Dashboard Answers

Static index. Not computed — exists so any exec opening the sheet immediately sees what it covers.

### 💡 Executive Summary

A high-level narrative of the week's performance. Now powered by **Gemini AI**, this section synthesizes metrics from across the entire report to generate dynamic HIGHLIGHTS, CONCERNS, and NOTES.

The AI analyzes the relationship between:
- **Throughput & Capacity**: Celebrates efficiency gains even when volume is lower due to PTO.
- **Behavioral Signals**: Recognizes proactive communication and accountability signals from Jira comments.
- **Planning Quality**: Highlights early delivery as a sign of commitment and quality.

If the AI is not configured (via `GEMINI_API_KEY`), it falls back to deterministic rule-based insights.

### 🏢 Company Signal

Company-wide WoW metrics.

| Metric                            | Formula                                                                                                                               | Interpretation                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Done Items (throughput)           | count of issues with `statusCategory = Done` and `resolutiondate` in the week                                                         | Raw delivery volume                                |
| Net Available Capacity (Hrs)      | (Sum of weekly IC capacity) − (Sum of PTO/Time Off hours)                                                                             | The true 'available' hours for the team            |
| Throughput per 100 Net Cap Hrs    | (Genuinely Done ÷ Net Available Capacity) × 100                                                                                      | Delivery efficiency normalized for leave/holidays  |
| Active Contributors               | distinct `assignee.accountId` on Done issues                                                                                          | People who delivered at least 1 item               |
| Items / Contributor               | Done Items ÷ Contributors                                                                                                             | Productivity normalized for team size              |
| Median Cycle Time (days)          | median of `(resolutiondate − created)` across Done issues                                                                             | Speed-to-value (lower is better)                   |
| Blocked Items                     | count of Done issues with any inward `issuelinks` (proxy for "is blocked by")                                                         | Delivery-risk proxy (lower is better)              |
| % Genuinely Completed             | Done items **not** resolved as Won't Do / Duplicate / Declined / Cannot Reproduce / Not a Bug / Rejected, divided by total Done × 100 | Shipped vs just closed                             |
| Hours Logged on Completed Work    | sum of `timespent` on Done issues ÷ 3600                                                                                              | Jira worklog hours (0 = no time tracking captured) |

### 🧠 Behavioral Insights

Keyword/sentiment analysis of `Comments (ADF Extracted)` to surface signals of ServiceRocket Leadership Behaviors.

| Behavior                | Example Keywords                                  | leadership Behavior Ref. | Interpretation                                     |
| ----------------------- | ------------------------------------------------- | ------------------------ | -------------------------------------------------- |
| Team Builder            | help, thanks, collaborate, shoutout               | 1.3                      | Proactive support and positive culture contribution|
| Deliberate/Decisive     | blocker, decided, priority, action                | 7.1, 7.3                 | Efficient decision making and barrier removal      |
| Proactive & Responsive  | update, resolved early, opportunity               | 9.4, 9.5                 | Anticipating needs and seizing delivery momentum   |
| Accountable             | delayed, my bad, fixed, commitment                | 10.1, 10.2               | Ownership of commitments and clear communication  |

### 🚨 Open Risk (state-of-backlog snapshot)

> **This section is a snapshot of today**, not a WoW comparison. The prior-week column is intentionally blank; the value appears in the latest-week column. Δ and % cells are gray because there's no comparison.

| Metric                                | Source                                                  | Meaning                                                |
| ------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------ |
| Overdue Still Open                    | JQL `statusCategory != Done AND duedate < now()`        | Items past their due date, not yet resolved            |
| Aged WIP                              | JQL `statusCategory = "In Progress" AND updated < -14d` | Items stuck in-progress with no updates for 14+ days   |
| Top 3 Oldest Overdue (narrative rows) | Overdue items sorted by days-overdue desc, top 3        | Named items with key, summary, days overdue, and Space |

If no overdue open items exist, the section collapses to a single "✅ No overdue open items." row.

### 💰 Revenue Protection Events (RPE)

**Definition** — a Revenue Protection Event is an item that was overdue at the time it was completed:

```
RPE ⇔ duedate < resolutiondate
```

This measures **backlog-clearing intensity** — how much aged work we retired.

| Metric                               | Formula                                                    |
| ------------------------------------ | ---------------------------------------------------------- |
| RPE Items Cleared                    | count of Done items where `duedate < resolutiondate`       |
| Avg Overdue Age at Resolution (days) | mean of `(resolutiondate − duedate)` days across RPE items |
| % of Completed Work That Was Overdue | RPE count ÷ total Done × 100                               |
| RPE Effort (hours logged)            | sum of `timespent` on RPE items ÷ 3600                     |

### ⭐ Top Epics Closed

Up to 5 epics resolved in the latest week, sorted by `resolutiondate` descending. Each row shows: index, key, truncated summary (80 chars), issue type, Space. Excludes non-delivery resolutions (Won't Do / Duplicate / etc.).

If no epics closed, shows a single "No epics closed this week — check 🎯 PRIORITY EPICS for kick-off / go-live movement." row.

### 📊 Space Breakdown

Same core metrics as Company Signal, scoped to each Space configured in `CONFIGJ.SPACES` (defaults: COE, R&D, Customer). Plus **RPE Items Cleared** per Space so you can see which Space is driving backlog retirement.

### 🎯 Priority Epics

Separates epic issue types:

| Row                 | Matched types (`issuetype.name`, lowercased) |
| ------------------- | -------------------------------------------- |
| Kick-off Epics Done | `kick-off epic` or `kick off epic`           |
| Go-live Epics Done  | `go-live epic` or `go live epic`             |
| Regular Epics Done  | `epic`                                       |

### 🔧 Workstream Rollup

Count by `issuetype.name` (Epic, Story, Task, Sub-task, Bug, Incident, …). Ordered: Epic → Kick-off epic → Go-live epic → Story → Task → Sub-task, then alphabetical for anything else. The Signal column labels each type's business meaning (Strategic initiative, Operational execution, etc.).

### ⚖️ Backlog Health (Delivered vs Added)

Compares outflow (Done items) to inflow (newly created items) in the same two-week window.

| Row                        | Formula                                         |
| -------------------------- | ----------------------------------------------- |
| Delivered (resolved items) | count of Done items resolved in the week        |
| Added (created items)      | count of items created in the week (any status) |
| Net (Delivered − Added)    | Delivered − Added                               |

- Positive net → backlog shrinking ✅ (capacity outpacing intake)
- Negative net → backlog growing ⚠️ (intake outpacing capacity)

A per-Space Net row follows the TOTAL row.

### 🔍 Data Hygiene

Signal-integrity checks — how much to trust the other numbers.

| Metric                             | Formula                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------ |
| % Unassigned (of completed)        | Done items with no `assignee` ÷ total Done × 100                                     |
| % Missing Due Date                 | Done items with no `duedate` ÷ total Done × 100                                      |
| % Non-Epic Items Missing Epic Link | non-epic Done items with no `customfield_10014` _and_ no `parent` ÷ total Done × 100 |

**Why this matters**: if `% Missing Due Date` is high (say 70%), the RPE numbers only reflect the 30% that _have_ due dates — interpret accordingly.

## Time windows

- Weeks are **Monday 00:00:00 → Sunday 23:59:59.999** in the Apps Script project's timezone.
- Exec Q&A compares the **2 most recently completed** weeks (configurable via `CONFIGJ.EXEC_WEEKS_BACK`).
- The broader Raw sheet covers `CONFIGJ.LOOKBACK_DAYS` days (default 28 — covers 3 full weeks + buffer).

## Data sources (JQL)

All queries run against `/rest/api/3/search/jql` (cursor-based pagination via `nextPageToken`). Every query is logged to the Apps Script Logger when the script runs — copy from there to reproduce.

### Completed work (main fetch, `fetchJiraIssues_`)

```jql
issuetype in (Epic, "Kick-off epic", "Go-live epic", Story, Task, "Sub-task")
AND statusCategory = Done
AND project NOT IN (TEMPLATE)
AND resolutiondate >= "{today − LOOKBACK_DAYS}"
AND summary !~ "to delete"
ORDER BY resolutiondate DESC
```

Results are then bucketed in-JS by `resolutiondate` into the Mon–Sun weeks.

### Created work (Backlog Health "Added", `fetchCreatedIssues_`)

```jql
issuetype in (...)
AND project NOT IN (TEMPLATE)
AND created >= "{exec week 1 start}"
AND created <= "{exec week 2 end}"
AND summary !~ "to delete"
ORDER BY created DESC
```

### Open at risk (🚨 Open Risk, `fetchOpenAtRiskIssues_`)

```jql
issuetype in (...)
AND project NOT IN (TEMPLATE)
AND summary !~ "to delete"
AND statusCategory != Done
AND (duedate < now() OR (statusCategory = "In Progress" AND updated < -14d))
ORDER BY duedate ASC
```

## Space classification

`getSpaceForIssue_(issue)` maps each Jira issue to a Space using `CONFIGJ.SPACES[].match` — exact match on:

- Uppercase `project.key`, OR
- Normalized `project.name` (lowercase, `&` → `and`, non-alphanumeric stripped, whitespace collapsed)

If nothing matches, the issue falls through to **`Customer`** (not "Other").

> **If R&D looks under-counted**: check which projects are appearing as "Customer" in the Jira Raw sheet column E. Typical cause: the actual Jira project key or name isn't in `CONFIGJ.SPACES[].match`. Fix by adding the real key(s) to that match array. Jira project keys are normally plain uppercase alphanumerics (e.g., `RND`) — hyphens like `RND-OPS` won't match a real project key.

## Limitations (what this sheet does NOT yet measure)

These are "Technic"-stage additions — they need data sources the current Jira instance doesn't have:

- **Availability / capacity utilization** — needs WFP-style planned hours per person per week. Not available in Jira.
- **Revenue categories (A/B/C/D)** — needs a custom field or label convention marking each issue as Direct Revenue / Renewal / Risk / Enablement. Not present yet.
- **Rolling median baseline** — the sheet currently compares W−1 vs W−2 only. An 8-week rolling median would better normalize for holidays, release cycles, and PTO.
- **Historical Open Risk trend** — the 🚨 Open Risk section is a today-snapshot. Reconstructing last week's risk state requires the issue changelog, which is not currently fetched.
- **Re-open / re-work detection** — requires the issue changelog.

## How to run

1. Open the Google Sheet; go to **Extensions → Apps Script**.
2. Run `setAPI__Jira()` once to store your Jira API token (token from <https://id.atlassian.com/manage-profile/security/api-tokens>).
3. Verify `CONFIGJ.JIRA_EMAIL` matches the token owner.
4. Run `previewWeekWindows()` → confirm the week bounds look right in the Logger.
5. Run `testJiraConnection()` → confirm issues return.
6. Run `runJiraEpicTracker()` → writes **Jira Raw**, **Weekly Report**, **Exec Q&A**, **Top Performers**.
7. Run `recreateExecQAOnly()` → refreshes **ONLY** the **Exec Q&A** tab (skips others).

Expected runtime: 30–90 seconds depending on issue volume.

## Troubleshooting

| Symptom                        | Likely cause                                                      | Fix                                                                                     |
| ------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Hours Logged = 0 everywhere    | Team isn't logging time in Jira                                   | Not a code issue — address worklog culture, or treat the metric as unavailable          |
| `% Missing Due Date` very high | Teams not setting due dates                                       | Data-culture issue; RPE numbers will only reflect items that _do_ have due dates        |
| R&D row shows very few items   | `CONFIGJ.SPACES[].match` doesn't list the real project keys/names | Check Raw sheet column E, add the real keys/names to the match array                    |
| Aged WIP always 0              | Jira may use non-standard status category keys                    | Confirm `statusCategory.key === "indeterminate"` for In Progress items in your instance |
| `401 Unauthorized`             | Token invalid or email mismatch                                   | Re-run `setAPI__Jira()`; verify `JIRA_EMAIL` matches the token owner                    |
| `400 Bad Request`              | JQL mismatch (e.g., unknown issue type)                           | Check `CONFIGJ.EXEC_ISSUE_TYPES` against the types in your Jira site                    |

## Why this sheet is the source of trust

1. **Deterministic** — same Jira state + same script = identical numbers.
2. **Auditable** — every JQL query is logged to the Apps Script Logger on each run.
3. **Transparent math** — no hidden spreadsheet formulas; all computation lives in [`Jira Backlog.js`](./Jira%20Backlog.js).
4. **No manual input** — the Exec Q&A tab is fully regenerated on each run (`clearContents()` + `clearFormats()` first). Anything an analyst types there will be erased on the next run.
5. **Signal integrity surfaced** — the 🔍 Data Hygiene section tells you up-front how much to trust the rest.

If a number looks wrong, the fastest path is:

1. Copy the JQL from the Logger output.
2. Run it against Jira directly (Issues → Advanced search → paste JQL).
3. Compare Jira's count to the sheet's value.
4. If they differ → it's an aggregation bug, not a fetch bug.
5. If they agree and the number still looks wrong → investigate the Jira data, not the script.
